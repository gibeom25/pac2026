# PAC 2026 문제점 정의

### 작업 목표
- AI 계층과 제어 계층을 연결하는 인터페이스를 만든다.

### 배경 — 왜 이 인터페이스가 필요한가
- AI 추론 계층은 결과 값의 생성 주기가 일정하지 않고, 추론 주기가 대략 10ms 수준이다.
- 제어 계층은 1ms 이하 주기(실시간 제어)를 안정적으로 유지해야 한다.
- 10ms(추론) vs 1ms(제어) — AI가 제어 주기를 직접 따라갈 수 없다는 게 핵심 제약이다.

**예시 상황**
> * 일반적인 상황에서는 제어 계층의 로봇이 일정한 제어 주기로 정해진 행동을 반복한다.
> * 이때 정지 지점(ex. 직진 선을 따라가는 로봇에서, 선의 끝 지점이 정해지지 않아 vision 기반 AI로 예측해야 하는 상황)을 예측하는 AI를 만들었다고 하자.
> * AI는 1ms 이하의 제어주기를 따라갈 수 없으므로 정지 신호를 판단해서 보내더라도, 실제로는 정지 지점을 지나친 뒤에야 멈출 수 있다.
> * 이는 실 제조 공정(ex. 용접)에서 큰 issue이며, 일정하지 않은 성과물을 낸다.
> * 이 상황을 보정할 수 있는 AI-제어 계층 간 기법이 필요하다.

### 작업의 정의
- AI 계층은 이미지를 입력으로 Action Chunk(size: 32)를 생성하는 모델이다.
- 작업은 **꺾인 직선(polyline)** 선을 Vision 센서만으로 따라가는 작업이다. (최초엔 sinusoidal 선으로 정의했으나, 실제 용접 공정이 직선 위주라는 점과 7번 문제를 근본적으로 줄이기 위해 변경.)
- 작업 중 3D 펜으로 선 위에 필라멘트를 분사해야 한다.
- 성능 지표는 뿌려진 필라멘트가 선을 얼마나 잘 덮었는가(coverage)이다.

### 핵심 파라미터 관계 (정의 필요)
위 네 숫자가 서로 어떻게 맞물리는지 명시돼야 한다:

| 파라미터 | 값 | 비고 |
|---|---|---|
| 제어 주기 | < 1ms | 고정 요구사항 |
| AI 추론 주기 | ~10ms | 매 추론마다 이만큼 걸림 |
| Chunk 크기 | 32 step | — |
| Chunk 내부 스텝 간격(dt) | **미정** | chunk가 실제로 몇 ms를 커버하는지 결정 |

- `chunk 전체 커버 시간 = 32 × dt`가 추론 주기(10ms)보다 **여유 있게** 커야 추론이 느려져도 버퍼가 안 고갈된다(아래 문제 1).
- `dt`가 제어 주기(1ms)보다 크면, 제어 계층은 청크의 각 스텝 사이를 **보간**해서 매 1ms마다 값을 만들어야 한다 — 이 보간 방식(선형/다항식 등)도 정해야 한다.

### 문제점
1. **버퍼 고갈**: action chunk가 다 소진될 때까지 다음 chunk가 안 오면, 다음 목표 지점을 예측 못 한 채 제어가 멈춘다.
2. **청크 경계 간극**: 새 chunk가 들어왔을 때 이전 chunk와의 사이에 속도/위치 불연속(간극)이 생길 수 있다. (→ 8번이 이 간극이 생기는 구체적인 원인 중 하나다.)
3. **트리거 신호의 불안정성**: 도포 작업에서는 on/off 트리거가 중요한데, chunk 내 미래 시점으로 갈수록 그 시점의 트리거 예측이 부정확해진다. 로봇이 선을 벗어나는 순간 즉각적인 트리거 on/off 전환이 필요한데, 이미 결정된 chunk 안에서는 즉각 반응이 안 되는 문제가 남는다.
4. **청크 교체/융합 방법 미정**: 새 chunk가 들어왔을 때 이전 chunk와 어떻게 교체·이어붙일지(끊고 바로 갈아탈지, 하던 걸 끝내고 갈아탈지, 블렌딩할지) 방법이 필요하다.
5. **청크 내부는 열린 루프(open-loop)**: chunk가 계획된 시점의 관측을 기준으로 미리 정해지므로, 실행되는 동안 실제 상황(로봇 위치, 외란, 선의 변화)과 무관하게 그대로 실행된다 — chunk가 길수록 이 구간이 길어져 오차가 누적된다.
6. **프로세스 간 실행 동기화**: AI와 제어가 별도 프로세스(실행환경 분리)로 돌 때, 양쪽이 같은 시간 기준을 공유해야 chunk의 유효기간/최신 여부를 올바르게 판단할 수 있다.
7. **(sinusoid 특유) 재동기화 위상 모호성**: 선이 주기 함수(sinusoid)이므로, 새 chunk를 이전 궤적에 이어붙일 때 위치만으로 매칭하면 같은 Y값을 갖는 다른 주기의 지점에 잘못 매칭될 수 있다 — 위치뿐 아니라 진행 방향(속도 벡터)까지 함께 봐야 모호성이 줄어든다.
8. **관측 시점과 적용 시점의 상태 불일치 → 진동(oscillation)**: 카메라는 추론을 "시작하는" 시점의 화면을 보고 action chunk를 만든다. 그런데 그 chunk가 실제로 제어에 반영되는 시점에는, 제어 계층이 이전 chunk로 그 추론 시간(~10ms)만큼 로봇을 이미 앞으로 진행시켜 놓은 상태다. 새 chunk의 각 스텝을 "관측 당시의 위치"를 기준으로 한 증분으로 그대로 적용하면, 로봇은 실제로 이미 지나온 지점을 향해 뒤로 갔다가 다시 앞으로 가는 식의 진동이 발생한다 — 추론 시간이 길어질수록, 혹은 그 사이 로봇 속도가 빠를수록 이 진동 폭이 커진다. (새 chunk의 시작점을 "관측 시점 위치"가 아니라 "chunk가 실제 적용될 것으로 예상되는 시점의 위치"로 재기준(anchoring)하면 완화할 수 있다 — 4번의 청크 교체 방법과 직접 연결된다.)

## 제안 해결 방법

### 1. 버퍼 고갈 → 안전지대 + exponential 감속 + 하한선
- 정상 진행은 chunk의 2/3 지점까지만 허용한다.
- 2/3 지점에 도달했는데 새 chunk가 아직 안 왔으면, 남은 구간을 **exponential하게 시간축을 늘려** 재생성한다(신호 전달 간격을 점점 늘리고 그 사이를 보간) — 32 스텝을 다시 만든다.
- 그래도 안 오면 다음 중간지점에서 또 한 번 늘려서 재생성 — 이 과정을 반복.
- **하한선**: 이 재생성을 무한정 반복할 수 없으므로, 최대 N회(또는 최대 지연시간) 넘어가면 더 이상 감속하지 않고 **완전 정지(HOLD)** 상태로 전환한다. (exponential 감속은 수학적으로 끝점에 점근적으로만 가까워지고 유한 시간에 도달하지 않기 때문에 하한선이 반드시 필요함.)
- **고도화(선택)**: 고정된 "2/3 지점" 임계값 대신, 아래 Kalman Filter 추정의 불확실성(공분산)이 일정 수준을 넘으면 감속을 시작하는 방식으로 바꾸면 더 원칙 있는 기준이 된다.

### 2. 청크 경계 간극 (= 4번, 8번과 동일 메커니즘으로 해결)
새 chunk 수신 시, 제어 계층에서 다음 절차로 시작점을 고른다:
1. 새 chunk의 32개 후보 지점 각각을 참조 경로(polyline)에 투영해서 **호 길이 진행률(progress)**을 계산한다 — `ai_layer/rl/reward.py::_point_to_polyline()`이 이미 이 계산(`perp_dist, progress, seg_idx`)을 제공하므로 재사용한다.
2. **단조증가 제약**: 직전까지 확정된 진행률(`last_progress`)보다 작은 후보는 전부 제외한다 (뒤로 가는 매칭 금지).
3. 남은 후보 중 **위치 거리 + 진행 방향(속도 벡터) 유사도**를 함께 점수화해서 가장 좋은 지점을 선택한다 (위치만 보면 7번 같은 모호성이 생길 수 있으므로 방향도 반드시 포함).
4. 선택된 지점부터 새 chunk 재생을 시작하고, 직전 속도와의 차이는 **짧은 구간 보간(blending)**으로 부드럽게 잇는다.
- 이 메커니즘이 **4번(청크 교체/융합 방법)**과 **8번(관측-적용 시점 불일치로 인한 진동)**을 동시에 해결한다 — 8번은 특히 단조증가 제약이 없으면 노이즈로 인해 역방향 매칭이 생겨 오히려 진동이 재발할 수 있으므로 더 중요하다.

### 3. 트리거 신호 불안정성 — 아이디어만 (본 과제 범위 밖, 후속 과제)
- 트리거는 chunk의 사전 계획을 따르지 않고 **매 제어 틱마다 실시간 재평가**한다 — 이미 AI 레이어에 있는 패턴(선에서 `off_seam_safety_dist`보다 멀면 chunk 내용과 무관하게 트리거 강제 OFF)을 일반화하는 방향.
- on/off 임계값에 **히스테리시스**(on 임계값 ≠ off 임계값)를 둬서 경계에서 깜빡이는 걸 방지.
- 노이즈가 많다면 raw 측정값 대신 Kalman Filter로 필터링된 이탈거리 추정치를 사용.

### 5. 청크 내부 열린 루프 — 아이디어만 (본 과제 범위 밖, 후속 과제)
- **Feedforward(AI chunk) + Feedback(실시간 보정) 2단 구조**를 제안: AI가 만든 chunk는 "큰 그림 계획"으로만 쓰고, 그 사이사이를 Kalman Filter(또는 단순 constant-velocity predictor)가 매 틱 실시간으로 미세 보정한다.
- 시간 여유가 된다면 짧은 구간에 한해 선형화된 LQR(MPC보다 훨씬 싼, 닫힌 형태 해를 갖는 최적제어)을 스트레치 목표로 검토.
- MPC는 매 제어 틱마다 최적화를 풀어야 해서 그 자체가 지터 요인이 될 수 있어 본 과제 범위에서는 보류.

### 6. 프로세스 간 실행 동기화 — 아이디어만 (지금은 불필요)
- 현재는 AI/제어가 같은 머신에서 `ipc://` 소켓으로 통신하므로 `CLOCK_MONOTONIC`을 양쪽 다 사용하는 것만으로 충분하다(동일 머신에서는 프로세스 간 자동으로 일치).
- 추후 AI와 제어가 서로 다른 머신에서 돌게 되면, 타임스탬프 비교 대신 **요청-응답 ID 상관관계**(`seq_id`/`snap_id` 같은 상관 ID 매칭) 방식을 고려.

### 7. Sinusoid 위상 모호성 → 해결됨
- 과제를 꺾인 직선(polyline)으로 바꾸면서 전역적인 "같은 Y값이 여러 번 반복"되는 상황 자체가 사라졌다.
- 추가로, 2번 해법(호 길이 기준 단조증가 + 방향 비교)을 적용하면 코너 부근에서 남을 수 있는 국소적 모호성까지 구조적으로 막히므로, **문제 상황 자체 제거 + 일반 해법 적용**의 이중 안전장치로 해결된다고 본다.

### 전체 아키텍처 반영
- **Feedforward**: AI 추론 계층이 만드는 Action Chunk (큰 그림 경로 계획)
- **Feedback**: 제어 계층에 Kalman Filter(혹은 constant-velocity predictor) 추가 — chunk 재동기화(2번), 열린 루프 구간 보정(5번), 버퍼 고갈 판단 고도화(1번), 트리거 노이즈 필터링(3번)에 공통으로 활용
- MPC/LQR 같은 더 무거운 최적제어는 계산 비용 문제로 본 과제에서는 보류, 후속 과제 아이디어로 남김

- **3**: 시뮬레이션에 있던 `off_seam_safety_dist` 강제 OFF 패턴을 배포 경로로 이식 + 히스테리시스 추가.
- **5**: 전부 신규 구현.

| | 기존 `choose_anchor()` | 신규 `anchor_resync.resync_start_index()` |
|---|---|---|
| 위치(레이어) | **AI 쪽** (`ai_node.py`가 chunk를 만들기 **전에** 호출) | **제어 쪽** (PointMass가 chunk를 받은 **후에** 호출) |
| 시점 | 예측 — "추론 끝날 때 로봇이 거기 있을 것" | 사후 확인 — "지금 실제로 로봇이 어디 있는지" |
| 탐색 | 없음. `commit.poses[-1]` 한 점을 그대로 신뢰 | chunk의 N개 후보 전부를 참조 경로에 투영해 탐색 |
| 모호성 방지 | 없음 | 단조증가(호 길이 진행률) 제약 + 진행 방향 비교 |
| 서로의 관계 | **대체되지 않음** — 그대로 1단계로 유지 | 1단계(`choose_anchor`) 위에 얹는 2단계 정밀 보정 |

실측 차이(동일 시드, baseline=`choose_anchor`만/제어쪽 보정 없음 vs proposed=2단계 전부 적용):
- 8번(역행) 발생: baseline **38회, 최대 18.7mm 후퇴** → proposed **0회**.
- 처음엔 baseline 구현에 실수로 "실제 현재 위치"를 그냥 가져다 써서 8번이 전혀 재현이 안 됐다 — `snap_id`로 "AI가 그 chunk를 만들 때 가정했던 위치"를 정확히 복원하도록 고친 뒤에야 문제 상황이 제대로 재현됐다(코드만 보면 맞아 보여도 실제로 돌려봐야 드러나는 종류의 버그였음).

**1 — `ChunkBuffer` vs 기존 `ControlMode.DRAINING`**
기존은 enum 값+주석뿐이라 "차이점"이랄 게 없었다(비교 대상이 없음) — `ChunkBuffer`가 처음으로 그 상태의 의미를 코드로 정의했다. 설계 과정에서 기존 문서/코드 어디에도 없던 내용을 하나 추가로 발견: `remaining_commit()`이 DRAINING 중의 **느려진 실제 속도**를 반영해야 한다는 것(그렇지 않으면 COMMIT_END 예측이 틀어져 8번이 재발). 이건 1번과 2/4/8번이 서로 몰래 간섭하는 지점이라, 둘 다 "따로는 맞는데 합치면 깨지는" 전형적인 통합 버그였다.

**3 — `TriggerLogic` vs 기존 `off_seam_safety_dist`**
기존은 단일 임계값(선에서 멀면 무조건 OFF)이고 AI 쪽 **시뮬레이션 전용** 코드에 있었다. 신규는 (a) 위치를 제어 쪽 인터페이스 모듈로 옮겨 배포 경로에서도 쓸 수 있게 하고, (b) 히스테리시스(on_tol≠off_tol)를 추가해 경계에서의 채터링을 막는다 — 기존엔 이 채터링 방지 자체가 없었다.

**5 — `ConstantVelocityKF` 전부 신규**
구현 중 실측으로 버그 하나 확인: 처음엔 위치/속도 공분산을 블록별로 손으로 근사했는데, 위치-속도 **교차공분산** 항이 빠져서 속도 추정이 전혀 안 됐다(등속 운동을 50 스텝 넣어도 속도 추정값이 계속 0). 표준 KF 행렬 전파(`P <- F P Fᵀ + Q`)로 바꾼 뒤에야 실측(참값 0.01 m/s)에 가깝게(0.0098 m/s) 수렴했다.
